# 미개발 기능·알려진 이슈·권장 로드맵

## 1. 우선순위 원칙

다음 작업은 사용자 정보 보호와 데이터 정합성을 우선합니다. UI 카피·시각 개선은 중요하지만, 관리자 API 공개·이메일 기반 결과 노출 같은 보안 이슈를 해결한 뒤 진행하는 것이 안전합니다.

## 2. 즉시 결정·정리할 항목

### 2.1 사용자 정의 가치 기능의 제품 정책 (결정됨 — Phase 39-C)

지휘부 결정: **결과 화면의 가치 교체는 유지하고, 1단계의 73번 카드 경로는 제거한다.**

근거는 §7.2다. 1단계를 분류로 바꾸면 "내 가치가 목록에 없다"는 불만은 줄지만 사라지지는 않는다.
진단의 마지막 지점에서 참여자에게 최종 권한을 남기는 것은 `docs/07`의 '자율성' 원칙과 맞는다.

| 항목 | 결정 | 상태 |
|---|---|---|
| 정식 카드 수 | 72개로 고정 | 유지 |
| `Sort.tsx`의 id 73·커스텀 입력 레거시 | **제거** | Phase 39-C 완료 |
| `custom-value-step3` 저장소 키 | **폐기** (쓰기·읽기 모두) | Phase 39-C 완료 |
| `Result.tsx`의 "나만의 가치 추가하기" | **유지** | 변경 없음 |
| `custom-value-result` 저장소 키 | **유지** | 변경 없음 |
| `values_assessments.customValue` 컬럼 | **유지** | 마이그레이션 없음 |

`customValue`에 값이 들어오는 경로는 이제 하나다 — 결과 화면의 교체. 이전에는 두 경로(1단계 추가·결과
교체)가 같은 컬럼을 채워 데이터 의미가 섞였다. 그 혼재가 해소됐다.

### 2.2 관리자 API 권한 보호

| 위험 | 현재 상태 | 권장 조치 |
|---|---|---|
| 전체 결과 조회 | `values.getAll`이 public | `adminProcedure` 적용 |
| 단일·일괄 삭제 | `values.delete`, `deleteMany`가 public | `adminProcedure` 적용, 감사 로그 추가 |
| 결과 이력 조회 | 이메일만 알면 `getByEmail` 호출 가능 | 로그인 소유권 또는 이메일 인증 구현 |
| 관리자 링크 | localStorage 이메일 비교 | UI 보조 수단으로만 유지, 서버 권한에 의존 |

| P3 | 다국어 | 카드 데이터·성찰 질문·UI 카피의 번역 버전 관리 |

## 4. 알려진 기술 부채

| 영역 | 현상 | 영향 | 개선 방향 |
|---|---|---|---|
| 단계 타입 | `Step`/`STEP_CONFIGS`는 과거 1~5 설정을 포함 | `Sort.tsx`는 1~3만 직접 사용 | 단계 타입을 카드 소팅/전체 여정으로 분리하거나 주석 명확화 |
| 레거시 73번 카드 | 데이터는 제거됐지만 코드와 주석 잔존 | 유지보수 혼란 | 정책 결정 후 관련 코드·키 일괄 정리 |
| 결과 자동 저장 | 세션 플래그 기반 중복 방지 | 여러 탭·새 세션에서는 중복 가능 | 서버 idempotency 키·세션 id 도입 |
| 로그 | 사용자 이름·이메일·가치가 콘솔에 기록될 수 있음 | 개인정보 노출 위험 | 운영 로그 비식별화·디버그 로그 제거 |
| 관리자 권한 | 프런트엔드 이메일 비교에 의존 | 데이터 노출·삭제 위험 | 서버 role 기반 권한 통제 |
| 문서 이력 | `USER_GUIDE.md`, `LOCAL_SETUP_GUIDE.md`의 일부 내용이 과거 기준 | 카드 수·프로세스 설명 불일치 가능 | 본 `docs/`를 최신 기준으로 유지, 기존 문서는 검토 후 통합·정리 |

## 5. 권장 실행 순서

### 1단계: 안전한 운영 기반

서버 관리자 권한, 결과 소유권 보호, 개인정보 안내를 먼저 구현합니다. 구현 후 실제 운영 DB 권한, 네트워크, 감사 로그를 점검합니다.

### 2단계: 데이터·기능 정합성

사용자 정의 가치 기능의 유지 여부를 제품 담당자와 결정합니다. 유지한다면 72개 표준 카드와 사용자가 쓴 보완 가치를 구분해 저장·표시하는 모델을 설계하고, 제거한다면 레거시 코드·DB 컬럼·UI를 단계적으로 없앱니다.

### 3단계: 안정성·검증

진단 단계 전이와 결과 저장에 단위 테스트·통합 테스트를 추가합니다. 특히 72개 카드, 10개 쌍대비교, 3개 최종 선택, 중복 저장 방지, 재시작 흐름을 자동화합니다.

### 4단계: 사용자 가치 확장

이메일 결과 발송, PDF, 워크숍 모드, 비식별 분석을 개인정보·권한 설계와 함께 추가합니다.

## 6. 작업 규칙

새 기능 또는 버그 보고를 받으면 다음 순서를 따릅니다.

1. `todo.md`에 검증 가능한 미완료 항목을 추가한다.
2. 해당 기능의 현재 화면·서버·DB·저장소 키를 확인한다.
3. 데이터 모델 변경은 `drizzle/schema.ts` → 마이그레이션 → DB 적용 순서로 진행한다.
4. 변경 후 `pnpm check`, `pnpm test`, 관련 수동 플로우를 실행한다.
5. 완료된 todo를 체크하고 `docs/`의 관련 문서를 같은 변경 단위로 갱신한다.
