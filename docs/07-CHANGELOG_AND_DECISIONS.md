# 주요 변경 이력과 제품 의사결정

## 1. 서비스의 핵심 진화

| 시기·단계 | 변경 | 결정 이유 |
|---|---|---|
| 초기 | 가치 카드 소팅 서비스 구축 | 한국어 가치 언어로 자기 탐색을 지원 |
| 카드 목록 정리 | 80개에서 72개 정식 가치로 축소·설명 보완 | 유사·중복 가치를 줄이고 한국 문화 맥락을 반영 |
| 진단 방식 개선 | 5개→3개 직접 선택 대신 쌍대비교와 최종 자유 선택 도입 | 미세한 우선순위를 관찰하되 알고리즘이 결정을 강제하지 않게 함 |
| 결과 관리 | 이름·이메일 기반 DB 저장·이력 조회·운영 화면 추가 | 재진단과 운영 활용 지원 |
| 결과 저장 안정화 | 세션 플래그로 무한 DB 저장 방지 | effect 재실행으로 인한 중복 저장 이슈 대응 |
| 카피 개선 | 1~5단계·인트로·결과를 직관·자기다움 중심으로 개편 | 당위가 아니라 내적 끌림에 따른 선택 유도 |
| 73번 카드 제거 | `나만의 가치 추가하기` 플레이스홀더를 카드 데이터에서 삭제 | 정식 카드 수를 72개로 유지하고 최초 흐름의 혼선을 줄임 |

## 2. 현재 카피의 기준

| 위치 | 기준 문구·의도 |
|---|---|
| 1단계 | “한 장씩 보여드립니다. 오래 생각하지 마세요” — 개수를 말하지 않는다. 세기 시작하면 반응이 아니라 계산이 된다 |
| 2단계 | “이것 없이는 정말 나답지 않아”인 10개 — 자기 동일시 강화 |
| 3단계 | 삶에서 “절대 타협할 수 없는” 5개 — 핵심성 강화 |
| 쌍대비교 | “머리가 아닌 가슴으로, 직관적으로” — 정답 없음 안내 |
| 최종 선택 | “당신의 인생을 대표할 3가지” — 순위는 참고, 최종 선택은 자유 |
| 결과 | “당신을 발견했습니다” — 가치가 의사결정의 나침반이라는 메시지 |

## 3. 유지해야 할 제품 원칙

> 가치 진단은 사람을 점수화하거나 정답을 판정하는 도구가 아니라, 사용자가 이미 가지고 있는 언어·경험·우선순위를 알아차리도록 돕는 성찰의 과정이다.

다음 원칙은 기능·카피·분석 기능이 늘어나도 유지합니다.

| 원칙 | 해석 |
|---|---|
| 비판정성 | 결과를 우열·성숙도·성격 유형으로 해석하지 않음 |
| 자율성 | 최종 선택은 사용자의 자유를 보장 |
| 투명성 | 저장·이메일·분석의 목적과 범위를 분명히 알림 |
| 재방문성 | 시간에 따른 가치 변화를 자연스러운 성찰로 존중 |
| 문화적 적합성 | 한국어의 관계·공동체·정서 맥락을 고려 |

## 4. 세미나 자료와의 관계

이 서비스는 가치 발견 그룹 코칭 세미나의 디지털 진단 도구로 활용될 수 있습니다. 세미나 자료의 핵심 흐름은 가치 발견 → 신념 탐색·재구성 → 삶의 적용 → 선언·실천입니다. 그러나 웹 서비스는 현재 **가치 발견과 결과 성찰**에 초점을 두며, 신념 재구성·WOOP·책임 파트너 기능을 제품 기능으로 구현하지는 않았습니다.

향후 세미나용 확장 기능을 만들 때는 개인 진단과 집단 워크숍 모드를 분리하고, 참가자의 결과를 퍼실리테이터에게 공유하는 경우 별도 동의·열람 권한·보존 기간을 설계해야 합니다.

### ADR-001. 저장소는 이원으로 두되, 원본을 실험장으로 삼는다 (R-2 → ③)

**결정일** 2026-09-03 · **상태** 확정

#### 배경

`loginheaven-jpg/value`는 2026-08-26 `futurenow-platform`으로 이식이 끝나 배포된 상태다
(퓨처나우 ADR-121, `dba74d5`). 업그레이드 지시서 v3(2026-09-02)는 그 사실을 참조하지 않고
원본을 제자리에서 개선했고, 검토 보고서가 이를 R-2로 지적했다. 지시서 v3.1은 C-0으로
"Phase 39 이상 보류"를 걸었으나 지휘 결정은 나지 않은 채 Phase 38~42가 원본에서 진행됐다.

두 제품은 **네 지점에서 정반대로 갈린다.**

| 항목 | 원본(이 저장소) | 이식본(futurenow) |
|---|---|---|
| 성찰 질문 | 72장 × 전용 2개 = 144문항 | 전원 공통 3개 |
| 1단계 | 한 장씩 3더미 분류 | 5화면 분할, 상한 없는 탐색 |
| 개인정보 | 이름·이메일 수집(§6.1 C안) | 계정 재사용, 신규 수집 0 |
| 카테고리 태그 | 1단계만 숨기고 3단계부터 노출 | 타입에서 제거, 참여자 표면 0 |

#### 선택지

| 안 | 내용 |
|---|---|
| ① | 원본을 독립 제품('코치의 나침반')으로 계속 가져간다 |
| ② | 이식본만 남기고 이 계획을 futurenow 지시서로 다시 쓴다 |
| ③ | **원본을 실험장으로 두고 검증된 것만 이식한다** |

#### 결정 — ③

②는 이미 성립하지 않는다. Phase 38~42가 원본에서 끝났고 네 지점의 격차를 오히려 벌렸다.
지금 ②를 택하면 그 작업 전부가 폐기 대상이 된다.

①과 ③의 차이는 **이식 의무가 있느냐**다. ①은 두 제품을 영구히 병행 유지한다는 뜻이고,
그 비용을 치를 근거가 없다. 퓨처나우 플랫폼이 제품이다 — 배포돼 있고, RLS로 차수·인도자
열람 범위를 관리하며, 문안 규범이 회귀 테스트로 잠겨 있다. 원본에는 그 기반이 없다.

반대로 원본은 **빠르다.** 플랫폼 제약이 없어 1단계 분류 전환·인쇄·진행자 가이드를 하루에
넣고 실측할 수 있었다. 그 속도를 버리는 것도 손해다.

따라서 ③이다. 원본은 UX를 먼저 시험하는 자리, 이식본은 제품.

#### 따라오는 것

| 항목 | 규율 |
|---|---|
| 제품 기준 | 퓨처나우 이식본이 **단일 진실**이다. 대외 배포·차수 운영은 그쪽 |
| 원본의 역할 | UX 실험과 자산 생산. 여기서 검증된 것만 이식 후보가 된다 |
| 이식은 자동이 아니다 | 원본의 변경이 이식본에 자동 반영되지 않는다. **건별로 판단**한다 |
| 격차 부채 | ③의 비용은 격차가 계속 벌어진다는 것이다. 이식 후보 목록을 이 문서에 유지한다 |

#### 현재 이식 후보

| 항목 | 판단 |
|---|---|
| 144문항 성찰 질문 | **이식한다.** 제품 중립 자산이고 `values.json` 한 파일이다(C-0이 그렇게 설계했다) |
| 1단계 분류 전환 | **후보.** 실기 검증 후 판단. 이식본의 5화면 분할을 대체할지는 별도 결정 |
| 결과 인쇄 | **후보.** 이식본에도 같은 필요가 있다 |
| 진행자 가이드 | **이식한다.** 문서 자산이다 |
| 개인정보 수집(§6.1 C안) | **이식하지 않는다.** 이식본은 계정을 재사용하며 신규 수집이 0이다 |
| 카테고리 태그 노출 | **이식하지 않는다.** 이식본은 참여자 표면에서 제거하기로 이미 결정했다 |

### ADR-002. 진입 시 개인정보는 현행 유지 + 동의 안내를 붙인다 (§6.1 → C안)

**결정일** 2026-09-03 · **상태** 확정

#### 배경

v1은 로그인도 정보 입력도 없이 시작했다. v2는 시작 화면에서 이름과 이메일을 요구하면서
개인정보 수집 동의 절차를 두지 않았다.

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A (현행) | 시작 화면에서 필수 입력 | 결과 유실 없음 | 진입 장벽, 동의 절차 부재 |
| B | 결과 화면에서 저장 시 입력 | 부담 없는 진입 | 미저장 이탈 가능 |
| C | 시작 화면 유지 + 동의 안내 추가 | 법적 정합성 | 장벽은 그대로 |

#### 결정 — C

세미나 운영상 진행자가 결과를 수집해야 하므로 B는 운영 리스크가 있다. 수집 시점과 항목은
그대로 두고 안내를 붙인다.

#### 이행

시작 화면에 수집 목적·보관 기간·삭제 문의처를 명시했다(`Intro.tsx`).

| 항목 | 문안 |
|---|---|
| 수집 목적 | 진단 결과를 저장하고 본인이 다시 조회할 수 있도록. 진행자가 운영을 위해 확인 |
| 보관 기간 | 삭제를 요청하실 때까지 |
| 삭제 문의처 | 진행자에게 말씀 (`PRIVACY_DELETION_CONTACT` 상수 한 곳) |

보관 기간을 "삭제를 요청하실 때까지"로 적은 것은 **지금 사실 그대로**다. 자동 삭제 로직이
없고 운영자가 지울 때까지 행이 남는다. 지키지 못할 기간을 적지 않는다. 자동 삭제를 넣기로
하면 그때 이 문안을 함께 고친다.

#### 아직 열려 있는 것 — Phase 39-B

v3.1 C-3은 `getByEmail` 소유권 검증을 §6.1과 **같은 Phase에 묶으라**고 했고, 검증 방식은
"이메일 인증 링크 · 조회 토큰 · 로그인 강제 중 택일"로 두었다. C안 확정만으로는 이 셋 중
무엇인지가 정해지지 않는다.

**'로그인 강제'는 C안과 모순된다** — C안의 단점란이 "장벽은 그대로"라고 적은 것은 새 장벽을
세우지 않는다는 뜻이다. 로그인을 요구하면 비로그인 참여자 흐름이 죽는다. 따라서 남는 것은
이메일 인증 링크와 조회 토큰 둘이며, **이 선택은 지휘 결정 대기 상태다.**

권고는 **조회 토큰**이다. 저장 시 1회용 조회 링크를 발급해 결과 화면에서 안내하면, 메일
발송 인프라 없이 소유권을 증명할 수 있다. 이메일 인증 링크는 발송 경로가 없는 현재 구성에서
새 인프라를 요구한다.
