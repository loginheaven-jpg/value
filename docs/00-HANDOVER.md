# 개발 인수인계: 다음 대화창을 위한 시작점

## 1. 이 문서의 목적

이 문서는 **코치의 나침반: 가치 발견 카드**의 개발을 다른 대화창 또는 다른 개발 환경에서 바로 이어가기 위한 실행 중심 인수인계 문서입니다. 새 담당자는 먼저 이 문서와 [`01-ARCHITECTURE.md`](01-ARCHITECTURE.md)를 읽고, 현재 동작을 확인한 뒤 [`06-BACKLOG_AND_KNOWN_ISSUES.md`](06-BACKLOG_AND_KNOWN_ISSUES.md)의 우선순위에 따라 작업을 시작해야 합니다. 세션을 **진행**하는 인도자용 문서는 별도입니다 — [`08-FACILITATOR_GUIDE.md`](08-FACILITATOR_GUIDE.md).

> 이 서비스의 핵심 원칙은 사용자가 사회적으로 "중요해야 한다"고 생각하는 항목이 아니라, **마음이 끌리고 자신다움을 느끼는 가치**를 발견하도록 돕는 것입니다. 카피·UI·프로세스를 수정할 때 이 원칙을 유지하십시오.

## 2. 현재 서비스 한눈에 보기

| 항목 | 현재 상태 |

| 서비스명 | 코치의 나침반: 가치 발견 카드 |

| 핵심 프로세스 | 72→20→10→5 선택, 5개 쌍대비교, 최종 3개 자유 선택 |

## 3. 현재 구현 상태

사용자 여정의 진단·쌍대비교·최종 선택·성찰 질문·결과 저장·이력 조회·관리 화면은 구현되어 있습니다. 구현된 사항과 보류 사항을 혼동하지 않도록 아래 표를 확인하십시오.

| 영역 | 구현 상태 | 핵심 파일 |
|---|---|---|
| 첫 화면·입력 검증 | 구현 | `client/src/pages/Intro.tsx` |
| 1~3단계 카드 소팅 | 구현 | `client/src/pages/Sort.tsx` |
| 5개 가치 쌍대비교 | 구현 | `client/src/pages/PairwiseComparison.tsx` |
| 최종 3개 자유 선택 | 구현 | `client/src/pages/FinalSelection.tsx` |
| 결과·성찰 질문·복사 | 구현 | `client/src/pages/Result.tsx` |
| 이전 결과 보기 | 구현 | `client/src/pages/MyResults.tsx` |
| 운영자 결과 관리 | 구현, **보안 보강 필요** | `client/src/pages/Admin.tsx` |
| 결과 DB 저장·조회·삭제 | 구현 | `server/routers.ts`, `server/db.ts` |
| 결과 이메일 전송 | 미구현 | 별도 메일 공급자·템플릿·동의 절차 필요 |
| PDF 생성 UI | 현재 비노출 | 패키지 의존성은 남아 있으나 사용자 흐름에서 숨김 |
| 안전한 운영자 권한 | 미완료 | 현재 UI 수준의 이메일 비교에 의존 |

## 4. 반드시 알아야 할 현재 의사결정

### 4.1 가치 카드 수와 사용자 정의 가치

정식 가치 데이터는 `client/public/values.json`의 **72개**입니다. 이전에는 id 73의 “나만의 가치 추가하기” 플레이스홀더 카드가 Step 3에 삽입되었으나, 사용자가 첫 진단 흐름에서 불필요하다고 판단하여 데이터 파일에서 제거되었습니다.

`Sort.tsx`의 id 73 사용자 정의 카드 경로는 **제거되었습니다**(Phase 39-C). `Result.tsx`의 교체 UI는 지휘부 결정에 따라 **유지**합니다 — 결과 화면에서 최종 3개 중 하나를 직접 쓴 가치로 바꿀 수 있습니다. `customValue`에 값이 들어오는 경로는 이제 이 하나뿐입니다. 자세한 내용은 [`06-BACKLOG_AND_KNOWN_ISSUES.md`](06-BACKLOG_AND_KNOWN_ISSUES.md)를 참조하십시오.

### 4.2 5단계라는 표현의 의미

사용자에게 보이는 카드 축소는 1~3단계이지만, 진단 전체는 다음 5단계입니다.

1. 72개 카드를 한 장씩 보며 네·글쎄요·아니요 세 더미로 **분류**한다(Phase 40).
   목표 개수를 제시하지 않으며, '네' 더미가 12~24장이면 다음으로 넘어간다.
2. 남은 카드 중 “이것 없이는 나답지 않다”는 10개를 고른다.
3. 삶에서 타협할 수 없는 5개를 고른다.
4. 5개를 10번 쌍대비교해 우선순위 단서를 얻는다.
5. 순위를 참고하되 자유롭게 최종 3개를 고른다.

### 4.3 결과 저장의 특성

결과 페이지는 `values-final`의 3개 가치를 로드한 뒤, `values-saved-to-db` 세션 플래그가 없는 경우 DB 저장을 시도합니다. 저장 호출 직전에 플래그를 넣고 실패하면 제거합니다. 이는 과거의 무한 저장 문제를 막기 위한 장치입니다. 다만 **동일 이메일의 중복 진단을 원천 차단하지는 않으며**, 같은 사용자의 재진단은 별도 레코드로 남을 수 있습니다.

## 5. 새 대화창에 바로 붙여 넣을 작업 재개 프롬프트

아래 문장을 새 대화창에 그대로 전달하면 맥락을 빠르게 복원할 수 있습니다.

```text
GitHub 저장소 loginheaven-jpg/value의 코치의 나침반: 가치 발견 카드 프로젝트를 이어서 개발해줘.
먼저 README.md와 docs/00-HANDOVER.md, docs/01-ARCHITECTURE.md,
docs/06-BACKLOG_AND_KNOWN_ISSUES.md를 읽고 현재 구현 상태를 파악해.

기술 스택은 React 19 + TypeScript + Tailwind 4 + Wouter, Express + tRPC 11,
Drizzle ORM + MySQL/TiDB다. 핵심 진단은 72→20→10→5, 5개 쌍대비교,
최종 3개 선택 흐름이다. 작업 전 todo.md에 새 항목을 추가하고,
소스 변경 후에는 pnpm check와 pnpm test를 실행해. 공개 저장소이므로
환경 변수·API 키·실사용자 데이터는 절대 커밋하지 마.
```

## 6. 권장 작업 시작 순서

새 담당자는 먼저 `pnpm install`, `pnpm check`, `pnpm test`, `pnpm dev`를 실행하여 기준선을 확인하십시오. 이후 운영자 API 권한 보호와 레거시 사용자 정의 가치 코드 정리 여부를 먼저 결정하는 것이 좋습니다. 이 두 이슈는 개인정보·데이터 정합성과 직접 관련되므로, 카피나 스타일 개선보다 먼저 처리할 가치가 있습니다.
